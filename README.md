# TravelBD — Personalized Travel and Hotel Recommendation for Bangladesh

A Flask academic prototype built around the seven datasets supplied for this project. It recommends destinations from interests, travel style, activities, facilities, budget, group size, origin, season and accessibility preference. A destination detail page lists hotel records and transport options available in the supplied data.

## Features
- **Two-level data model:** a *destination* is a district (64) where a traveller stays; the 78 rows in `destinations_cleaned.csv` are *areas* inside it (e.g. "Lalbagh Fort & Old Dhaka" is an area of the Dhaka destination); individual *attractions* (Lalbagh Fort, Ahsan Manzil …) are the child rows of `itinerary_attractions.csv`. The destination layer is derived at start-up by `build_places()` in `app.py`, so admin edits to areas, hotels or attractions still flow through.
- Interests are chosen from chips built from the dataset's destination types; ranking blends TF-IDF text similarity with an exact type match.
- Results → one click to hotels + a day-wise plan that reuses days, budget, group size and interests.
- TF-IDF content-based destination matching using destination name, district, type, attractions, activities, season and accessibility text.
- Hybrid ranking: `Score = w1*CBF + w2*CF + w3*Popularity + w4*Budget` (content match incl. season, similar-traveller collaborative filtering, rating/volume/BanTABSA popularity, budget fit). Weights are tuned on validation data (`python -m ml.tune_hybrid`) and stored in `artifacts/hybrid_weights.json`; see `HYBRID_MODEL.md` for the method, results and caveats. CF is learned from synthetic trips until real survey data is supplied, so its weight is capped.
- Hotel ranking using nightly price where available, rating, requested facility overlap and supplied review-count signals. Official BPC listings for the selected destination are always surfaced even when their rate/rating is not provided.
- BanTABSA review ratings and aspect sentiment are summarized by location and provide a small (5%) destination-ranking signal where location coverage matches. Anonymized BanTABSA hotel IDs are not joined to named hotels.
- Transport choices filtered by destination, origin when a direct origin match exists, and travel season.
- Day-wise itinerary planner with morning/afternoon/evening slots, travel-style and interest matching, estimated visit duration/cost, and a simple proximity-aware ordering of stops.
- Generated `itinerary_attractions.csv` from the destination highlights, supplied Bangladesh tourism geodata, and matching district-level suggestions from the tourist chatbot dataset.
- Model & Data page explaining data provenance and limitations.

Open a terminal in the `travelbd_full_project` folder:


## Important dataset caveats
- The review file has 10,000 records, but most are explicitly labelled `Synthetic placeholder`. Treat those as demonstration data, not genuine real-world customer reviews.
- The hotel file has 487 rows, including 463 synthetic placeholders and 24 official BPC listings. Official listings are surfaced for their associated destination even when room rate or facilities are missing.
- `BanTABSA.csv` contains 1,242 Bengali hotel reviews, 31 anonymized hotel IDs and 9 locations. Its rating/sentiment summaries are location-level, not ratings for any named BPC hotel.
- Destination daily budgets and transport fares/times are supplied estimates, not guaranteed current prices.
- `merged_dataset.csv` and `bangladesh_tourism_dataset.xlsx` are preserved for reference/audit. The app uses the separate tables to avoid counting duplicated joined rows as separate records.
- `tourismdatasetbd_bn.json` contains 13,813 tourism place records. The itinerary builder associates geolocated records within 5 km of the nearest destination centre; these associations can be approximate. Destination highlight lists are preserved even when individual coordinates are not available.
- `itinerary_attractions.csv` is generated by `python train_model.py`; it includes estimated visit durations and attraction expenses for demo planning. These are heuristics, not official prices or verified visit durations.
- Itinerary schedules are suggestions. They do not verify opening hours, local traffic, travel time between attractions, weather, or live entry fees. Some place coordinates/associations are approximate.
- This project does not make bookings or check live availability.

## Main files
- `app.py`: Flask routes and recommendation ranking.
- `train_model.py`: cleaning, aggregation, attraction dataset generation and TF-IDF model training.
- `build_itinerary_dataset.py`: creates the itinerary-ready attraction table from the supplied datasets.
- `itinerary.py`: preference-aware, constraint-based day-wise itinerary generation.
- `data/`: original uploaded files plus cleaned tables created by training.
- `artifacts/`: saved TF-IDF model and training report.

## Admin dashboard (persistent CRUD)

This version adds a protected admin area for destinations, itinerary attractions, hotels and dataset summaries.

1. Install dependencies in your project virtual environment:
   ```powershell
   py -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   ```
2. Start the app with `python app.py` and open `http://127.0.0.1:5000/admin`.
3. There is ONE sign-in page (`/login`) for users and admins. Admins are created or promoted only from the terminal (no public admin sign-up, no hard-coded password): `python manage.py create-admin` or `python manage.py promote <email>`. Other commands: `demote`, `reset-password`, `list-admins`. Admins are sent to the dashboard after sign-in; normal users get a 403 on `/admin`. Login locks for 5 minutes after 5 failed attempts.
4. The admin data store is `instance/travelbd_admin.sqlite3`. Editable records are also synced to the CSV files used by the project. The app creates a local session secret in `instance/secret_key.txt`.
5. Destination edits rebuild the TF-IDF destination features; attraction edits refresh the itinerary planner's attraction data; hotel edits refresh the hotel recommendation data. The Dataset Overview page shows row counts, columns, missing values and available source labels.

### Data files managed by the admin

- Destinations: `data/destinations_cleaned.csv` (the raw `data/1_destinations.csv` is no longer overwritten by admin edits)
- Itinerary attractions: `data/itinerary_attractions.csv` (this is the attraction table used by the day-wise itinerary planner)
- Hotels: `data/hotels_cleaned.csv`; official BPC rows are also exported to `data/bpc_hotels_cleaned.csv`

SQLite is the persistent admin store once initialized. If you re-run `train_model.py` and want its fresh output to replace the admin store, run `python manage.py reseed` (it backs up the database first); `train_model.py` prints a reminder when this applies. **Do not rerun `python train_model.py` after making admin edits unless you have backed up your data**: that preparation script rebuilds cleaned files from the original source datasets and can replace admin changes. Use the Admin Dashboard's “Refresh model features” action to rebuild destination TF-IDF features without rebuilding the source datasets.

Admin-added prices, visit durations and source labels must be accurate and appropriately caveated. A source label does not independently verify a listing; keep official URLs and never invent missing prices or facilities.

## User authentication and saved travel data

The project includes a simple user account system in addition to the separate admin login.

- Open `/register` to create a user account with name, email and password.
- Open `/login` to sign in and `/logout` to sign out.
- Open `/profile` to update name, optional phone, home district and travel interests.
- While signed in, destination recommendation searches are saved to the SQLite database.
- While signed in, generated day-wise itineraries are saved and can be revisited from the profile page.
- The admin dashboard shows the number of registered accounts.

User and admin passwords are stored as Werkzeug password hashes, not plain text. The SQLite database at `instance/travelbd_admin.sqlite3` stores accounts, profile details, saved searches and itineraries. Do not delete the `instance` directory if you want to preserve those records. Back up this directory regularly. The current prototype does not include email verification, password reset, or production deployment hardening; use it locally for the capstone demo unless those protections are added.

## Quick start (Windows)
1. Double-click `run.bat` (first run creates `.venv` and installs requirements; later runs just start the site).
2. Create an admin once, in a terminal: `.venv\Scripts\activate` then `python manage.py create-admin`. Sign in at /login (same page for everyone).

Set `TRAVELBD_DEBUG=1` before `python app.py` only if you want Flask debug mode.

## Registration with email OTP + mobile number
- Sign-up asks for name, email, Bangladeshi mobile number (01XXXXXXXXX or +8801XXXXXXXXX) and password, then emails a 6-digit code. The account is created only after the code is verified (expires in 10 minutes, 5 wrong tries, 60-second resend wait). Email and mobile number must each be unique.
- **Demo mode:** if email is not configured, the code is printed in the terminal running the site.
- **Real email (Gmail example):** copy `instance/email_config.example.json` to `instance/email_config.json` and fill it in. Use a Gmail *App Password* (Google Account > Security > 2-Step Verification > App passwords), not your normal password. Environment variables TRAVELBD_SMTP_HOST / _PORT / _USER / _PASSWORD / _FROM also work. Never share or commit this file.
- The mobile number is collected and format-checked but not SMS-verified (SMS needs a paid gateway).

## Forgot password
Sign in page > Forgot your password? Enter your email, receive a 6-digit code (10 minutes, 5 tries, 60-second wait between requests), then choose a new password. The site shows the same message whether or not the email has an account. Works for admins too. Terminal fallback: `python manage.py reset-password <email>`.


## Evaluation
`python evaluate.py` runs a persona-based sanity check (6 personas x 3 budgets) and compares the current ranking with the previous formula, cheapest-first, most-reviewed-first and random order (precision@5 on destination type, and share of results within budget). Results are written to `artifacts/evaluation_report.json`. The labels come from the same destination table the model reads, so absolute numbers are optimistic; use it to compare variants, and confirm with a small user study before making claims about real travellers.

## Security notes
- `instance/` holds your secrets (`email_config.json`, `secret_key.txt`) and the user database. It is git-ignored; never zip or share it. Use a Gmail App Password and revoke it if it is ever exposed.
- Set `TRAVELBD_HTTPS=1` when serving over HTTPS so the session cookie is marked Secure. Set `TRAVELBD_SECRET_KEY` to supply the session key from the environment instead of the file.
- OTP emails are limited to 8 per IP per hour, in addition to the 60-second per-address cooldown. Counters are in memory and reset on restart.


## Data quality tools (added)
- `python enrich_attractions.py [--dry-run]` tops up thin destinations (fewer than 12 attractions) with real, rated places from `tourismdatasetbd_bn.json` found within 25 km of an area centre (>= 3 ratings, >= 3.5 stars). Safe to re-run; writes to the admin database and `data/itinerary_attractions.csv`.
- `python import_hotels.py --report` lists districts with no real hotel; `python import_hotels.py my_hotels.csv [--dry-run]` validates and imports real hotels (template: `data/real_hotels_template.csv`; every row needs a source URL; blanks are allowed, guesses are not).
- Hotel ranking: real listings are always shown first; synthetic rows appear only as labelled "Demo record" fillers.
- Destination ratings now come from visitor ratings of attractions in the tourism geodata (rating-count weighted and shrunk toward the national mean). The synthetic 10,000-row review file is no longer used for ranking.


## Public landing page, account access and per-user menu rights

- The home page and Model & Data page are public so visitors can learn about TravelBD before registering. Destination previews/details remain browsable publicly.
- Running a personalized destination recommendation requires signing in. Generating a day-wise itinerary also requires signing in. Signed-in users can save searches and itineraries to their own profile.
- The admin dashboard reports registered normal users, unique accounts that logged in today, total login events today, unique accounts active within 7 days, and users who have never logged in. These are login-activity counts, not a guarantee of currently open browser sessions.
- Open Admin Dashboard → User management & menu rights to search users and manage individual menu permissions. Unchecked menus are hidden in navigation and protected on the server. New user accounts default to having all user menus enabled until an admin changes them. Admin accounts always have full access.
- Login activity is stored in `login_events`; `users.last_login_at` stores the latest successful login. Existing SQLite databases are migrated automatically when the app starts.
- Create an administrator from the project folder with `python manage.py create-admin`. Do not publish the database or instance secrets.
